EPIC 1
UNS Core Service & API
DESCRIPTION:
Design and build the foundational Node.js/PostgreSQL service, including the routing engine, template system, and public API that all product teams and channel adapters will depend on. This is the critical-path foundation for the entire program.
COMPLEXITY:
High
DEPENDENCIES:
None
STORY 1A
Service scaffolding & infrastructure setup
As a platform engineer, I want a fully scaffolded Node.js service deployed on AWS via the standard CI/CD pipeline, so that the team has a running baseline to build channel adapters and routing logic against.
COMPLEXITY
Medium
DEPENDS ON
None
SUGGESTED ACCEPTANCE CRITERIA
Node.js service repo created with linting, testing, and CI/CD pipeline configured; service deploys successfully to a dev environment on AWS.
PostgreSQL database provisioned with migrations tooling in place; connection verified from the service.
Health check endpoint returns 200 and is reachable from the internal network.
STORY 1B
Notification routing engine
As a product engineer, I want a routing engine that accepts a notification event and dispatches it to the correct channel adapter(s) based on the event type and user preferences, so that the right notification reaches the right channel without duplicate firing.
COMPLEXITY
High
DEPENDS ON
1A — Service scaffolding
SUGGESTED ACCEPTANCE CRITERIA
Routing engine correctly dispatches a single event to one or more channel adapters based on a configurable rules schema; routing logic is unit-tested with ≥90% coverage.
Duplicate suppression logic prevents the same notification from firing more than once per event per user per channel.
Routing decisions are logged to the delivery log table with event ID, channel, and timestamp.
STORY 1C
Template management system
As a product engineer, I want a centralized template management system that stores and renders notification templates for all channels, so that content can be managed in one place without channel-specific template stores.
COMPLEXITY
High
DEPENDS ON
1A — Service scaffolding
SUGGESTED ACCEPTANCE CRITERIA
Template CRUD API supports creating, retrieving, updating, and versioning templates per channel type (email, push, in-app).
Template rendering engine accepts a template ID and a variable payload and returns a rendered output; rendering is tested for all three channel types.
Templates are stored in PostgreSQL; prior versions are retained and retrievable for audit purposes.
STORY 1D
Public notification API (v1)
As a product team engineer, I want a documented REST API I can call to trigger any notification type for a user event, so that I do not need to integrate with multiple notification systems.
COMPLEXITY
High
DEPENDS ON
1B — Routing engine, 1C — Templates
SUGGESTED ACCEPTANCE CRITERIA
API accepts a POST request with event type, target user ID, channel(s), and variable payload; returns a 202 Accepted with a notification event ID.
API enforces authentication (API key or service token); unauthenticated requests return 401.
API input is validated with clear error responses (400) for malformed requests; schema is published in OpenAPI format.
STORY 1E
Delivery logging & status tracking (data layer)
As an ops engineer, I want every notification dispatched to be persisted with its delivery status and outcome, so that we have a single source of truth for notification delivery across all channels.
COMPLEXITY
Medium
DEPENDS ON
1A — Service scaffolding, 1B — Routing engine
SUGGESTED ACCEPTANCE CRITERIA
Delivery log table captures: event ID, user ID, channel, template ID, dispatch timestamp, delivery status (sent / delivered / failed / bounced), and channel-specific metadata.
Status updates are written asynchronously on delivery callbacks from SendGrid, Firebase, and WebSocket; no delivery is left in a permanent pending state without a timeout.
Log records are queryable by user ID, event type, channel, and date range with response times under 500ms for typical ops queries.
EPIC 2

DESCRIPTION:
Migrate all transactional email logic currently owned by the Platform team — including SendGrid integration, email templates, and user preference logic — into the UNS, then cut over traffic with zero downtime.
COMPLEXITY:
High
DEPENDENCIES:
1 — UNS Core Service & API
STORY 2A
Email channel adapter (SendGrid)
As a platform engineer, I want a UNS email channel adapter that sends messages via the existing SendGrid integration, so that the UNS can deliver transactional emails without changing the delivery provider.
COMPLEXITY
Medium
DEPENDS ON
1D — Public API, 1E — Delivery logging
SUGGESTED ACCEPTANCE CRITERIA
Adapter sends rendered email templates via SendGrid API; delivery receipts and bounce callbacks are written to the UNS delivery log.
Adapter handles SendGrid rate limits and transient errors with retry logic (configurable max retries, exponential backoff).
Integration test suite covers successful send, bounce, and rate-limit scenarios.
STORY 2B
Email template migration
As a platform engineer, I want all existing transactional email templates migrated and validated in the UNS template management system, so that email content is served from the new centralized store before cutover.
COMPLEXITY
High
DEPENDS ON
1C — Template management, 2A — Email adapter
SUGGESTED ACCEPTANCE CRITERIA
All existing transactional email templates inventoried, imported into the UNS template store, and rendered output validated against the legacy equivalent by QA.
No rendering regressions: visual diff testing confirms parity for all migrated templates.
Templates reviewed and signed off by the Platform team before cutover.
STORY 2C
Email preference logic migration
As a user, I want my existing email notification preferences to be respected after the migration, so that I do not receive emails I had previously opted out of.
COMPLEXITY
Medium
DEPENDS ON
5A — Preference data model, 2A — Email adapter
SUGGESTED ACCEPTANCE CRITERIA
All user email preference records migrated from the legacy Platform system to the UNS preference store; no data loss confirmed by row count and spot-check validation.
UNS routing engine suppresses email notifications for users with email opted-out before sending to the adapter.
Migration script is idempotent and can be re-run without creating duplicates.
STORY 2D
Parallel traffic validation (email)
As an engineering lead, I want the UNS to receive mirrored email traffic in parallel with the legacy system for a defined validation period, so that delivery fidelity is confirmed before hard cutover.
COMPLEXITY
High
DEPENDS ON
2A, 2B, 2C — Email migration stories
SUGGESTED ACCEPTANCE CRITERIA
Shadow mode is enabled: UNS processes all email events in parallel with the legacy system; only the legacy system actually delivers during this period.
Delivery success rate, bounce rate, and error rate in UNS are within 0.1% of the legacy system over the validation window.
Validation sign-off documented by Platform team lead and QA before cutover proceeds.
STORY 2E
Platform team traffic cutover (email)
As a platform engineer, I want email traffic fully routed through the UNS and the legacy email system deactivated, so that the Platform team no longer owns a separate email notification system.
COMPLEXITY
Low
DEPENDS ON
2D — Parallel validation
SUGGESTED ACCEPTANCE CRITERIA
100% of email traffic routed through UNS with no fallback to legacy system; legacy email system set to read-only / inactive.
Zero increase in email delivery failure rate in the 72 hours post-cutover.
Cutover runbook executed and rollback plan confirmed as available.

Project Brief: Unified Notification Service
Project Name: Unified Notification Service (UNS)
Date: June 4, 2026
Project Manager: TBD

Overview:

The engineering organization currently has three separate notification systems that evolved independently: one for transactional emails (owned by the Platform team), one for push notifications (owned by the Mobile team), and one for in-app alerts (owned by the Frontend team). Each has its own infrastructure, its own logic for user preferences, and its own delivery monitoring. This fragmentation causes duplicate maintenance overhead, inconsistent user experiences when multiple notification types fire for the same event, and no single source of truth for notification delivery status.
The Unified Notification Service project will consolidate all three systems into a single, centralized service that handles routing, templating, user preference management, and delivery tracking across all notification channels — email, push, and in-app.

Goals:

Reduce notification-related engineering maintenance overhead by consolidating three systems into one
Eliminate duplicate or conflicting notifications firing for the same user event
Provide a single API that any product team can call to trigger any notification type
Give users a single preference center to manage all notification settings
Provide ops and support teams with a unified delivery tracking dashboard

Scope:

In scope:

Design and build the Unified Notification Service API
Migrate transactional email logic from the existing Platform notification system
Migrate push notification logic from the existing Mobile notification system
Migrate in-app alert logic from the existing Frontend notification system
Build a user notification preference center (web UI)
Build an internal delivery tracking dashboard for ops and support use
Decommission the three legacy notification systems after migration
Documentation and runbooks for the new service

Out of scope:

SMS notifications (future phase)
Marketing or promotional email campaigns (owned by a separate marketing automation platform)
Native mobile app UI changes beyond what is required for the push migration

Teams Involved:

Platform Engineering
Mobile Engineering
Frontend Engineering
DevOps
QA
UX Design
Product Management
Security
Customer Support (stakeholder)
Engineering Leadership

Technical Context:

New service will be built in Node.js with a PostgreSQL database for preference storage and delivery logs
Push notifications will use the existing Firebase integration
Email delivery will use SendGrid
In-app alerts will use a WebSocket connection to the existing real-time infrastructure
Service will be deployed on AWS via the standard CI/CD pipeline
All three legacy systems must remain operational during migration to avoid notification downtime

Constraints:

Migration must be completed with zero downtime for end users
Legacy systems cannot be decommissioned until 100% of traffic has been validated on the new service
Q4 product roadmap features that depend on notification capabilities cannot be blocked by this migration
Security review required before the new service handles any PII (user email addresses, device tokens)

Success Criteria:

All three legacy notification systems decommissioned by end of Q4 2026
Zero increase in notification delivery failure rate post-migration
Single notification preference center live for all users
Internal delivery tracking dashboard in use by ops and support teams
New service API adopted by at least two product teams beyond the migration scope
